### T1.1 — A payroll period can be permanently bricked [converged 3, verified]

- `rejected` has **no exit transition** — `backend/app/services/run_workflow.py:751-755`
  concedes "rejected is a dead-end until an explicit recovery transition is added."
- The partial unique index `ux_payroll_runs_org_period_primary`
  (`backend/app/models/payroll_runs.py:120-126`, `WHERE original_run_id IS NULL`)
  blocks creating a replacement run for the period — `create_run` always inserts a
  draft with no `original_run_id` (`services/payroll_runs.py:482-503`) → 409s forever.
- Even `calculated` is terminal for edits: `_require_draft`
  (`services/payroll_runs.py:437-439`) freezes roster and all `payroll_run_inputs`
  after the first calculate (`:637,824,909`); `withdraw` returns to `calculated`,
  not `draft` (`run_workflow.py:640`). Any input/roster error found post-calculate is
  unrecoverable — the period yields the same wrong result or is abandoned.
- Frontend compounds it: `isCalculateAllowedStatus` includes `"rejected"`
  (`frontend/src/lib/api/payroll-runs.ts:75-77`), so the UI shows an enabled
  "Recalculate" button that is a guaranteed 409
  (`services/run_calculation/command.py:41` allows only `{draft, calculated}`).
  Test `pay-runs.test.tsx:571-592` pins the wrong contract.

**Fix:** design decision — add `rejected → draft` (and/or `calculated → draft`)
reopen transition, keeping run versions append-only; or let `create_run` supersede
a `rejected` run via `original_run_id`. Until then, remove `"rejected"` from the
frontend allowed set and fix the test row.

### T1.2 — Masked `••••XXXX` values written back as real data [verified]

- Backend masks sensitive fields as `••••<last4>`
  (`backend/app/schemas/employees.py:36-44`, applied at `:253-255,291-295`) unless the
  caller holds `reveal_sensitive_fields`.
- `frontend/src/pages/employees/ScheduleChangeDialog.tsx:143-171` prefills those
  masked values into editable inputs (`pan`, `pran`, `gpf_account_number`,
  `epf_number`, `pension_account`, `account_number`), and `buildBody` posts them
  back (`:183-198,215-222`). Write schemas accept any non-empty string; no `••••`
  guard exists anywhere.
- **Any write-capable role without `reveal_sensitive_fields` corrupts** — not just
  `payroll_preparer` (which holds `manage_master_data` and can never reveal,
  `auth/capabilities.py:55-64`). Every masked-field edit stores `••••234F` as the
  real PAN/account, invisibly (the masked view looks identical afterwards).

**Fix:** (a) never prefill masked values into editable inputs — require reveal, or
use "leave blank to keep" semantics; (b) backend safety net: reject values starting
with `••••` on write.

### T1.4 — Negative money flows through to posted payroll [converged 4, verified]

- `validate_run_inputs` (`backend/app/domain/payroll/validation.py:303`) — the only
  place `negative_amount` is rejected — has **zero production callers**; only tests
  call it (`backend/tests/...` only). `command.py` calls neither it nor an
  equivalent.
- `PayrollRunInputUpsert.amount` (`schemas/payroll_runs.py:166`) and all master-data
  money fields (`schemas/pay_setup.py:190-432`, `schemas/employees.py:96`) have no
  `ge=0`; no DB CHECK constraints on `recurring_instruction_versions.amount/rate`,
  `advance_installment_versions.*`, `component_rate_versions.*`,
  `accommodation_charge_versions.*`, `employee_pay_versions.basic_pay`.
- `validate_run_result` checks only `net<0` (error) and `line>gross` (warning) — a
  **negative deduction line increases take-home** and passes submit
  (`run_workflow.py:552-562`) + post (`run_posting.py:345-347`) cleanly.
- Unbounded values (> column precision) crash via asyncpg `DataError` → generic 500;
  `services/db_errors.py` maps only `IntegrityError`.
- **Carve-out required:** `validation.py:255-259` deliberately exempts
  `one_time_adjustment` components from `negative_amount` — negative amounts are a
  legitimate feature there. The `ge=0` bounds must not be applied blindly to that
  calc kind (or to inputs/versions targeting it). Conversely, roster
  `da_percent`/`hra_percent` are already bounded (`schemas/payroll_runs.py:119,125`
  + DB CHECKs `models/payroll_runs.py:200-205`) — don't duplicate.

**Fix:** wire `validate_run_inputs` into `calculate_run_command` (block on
error-severity findings); add `ge=0`/upper bounds matching `Numeric(12,2)`/
`Numeric(9,4)` precision **except** `one_time_adjustment`-targeted values; add DB
CHECKs; map `DataError` → 422 in `main.py`.

### T1.5 — Employer contribution↔transfer pairing enforced one way only [verified] — *needs design sign-off*

`backend/app/domain/payroll/engine.py:189-224`: a `transfer_of` pointing at a
missing/mismatched contribution raises (good), but (a) a non-excluded
`employer_contribution` with no transfer line stays in `gross_total`/`net_payable`
(`:141-155`) — the employee is **paid employer money**; (b) N transfer lines can all
pair to the same contribution via the same equality check — the deduction is counted
N times. `validation.py:330-442` has no transfer check either.

**Fix:** after collecting contributions, verify every non-excluded
`employer_contribution` is the `transfer_of` target of exactly one non-excluded
transfer (or enforce Σtransfers-per-target == contribution); add the same pairing
check to `validate_run_result`.

### T1.6 — Recoveries never complete and cannot be terminated [converged 2, verified]

- `services/run_calculation/resolution.py:336-359` emits
  `loan_installment_recovery` for the full `installment_amount` whenever an active
  installment version exists — it reads only `amount`/`id`, never
  `installments_recovered_opening >= installments_total`; nothing increments the
  counter on posting (only set at version-create, `services/pay_setup/advances.py:
  101-186`). Reports show a frozen "1/24" forever (`reports/families/recovery.py:
  301-330`); `installment × total` is never bounded by `principal` (`:46-60`).
- No `end_on`/terminate path for advances or accommodation charge versions — an
  employee who vacates quarters cannot stop accommodation charges; only recurring
  instructions call `terminate_open_version`.

**Fix:** skip emission when `recovered >= total`; validate
`installment × (total − opening) <= principal`; add a terminate/`end_on` path
(reuse `terminate_open_version`); decide which step advances the counter.

### T1.7 — `ENVIRONMENT` fails open; weak secrets honored in production [converged 3, verified]

- `config.py:99-100`: `is_production` is literal `environment.lower() == "production"`.
  Any other value — `staging` (documented in `deploy/.env.example`), `prod`, a
  typo — silently disables: `DEV_AUTH_BYPASS` rejection, required-secret checks,
  `Secure` cookie flag (`auth/session.py:71,81`), docs gating (`main.py:287-289`),
  and the auth-bypass gate (`adapters.py:281-297`, `routes/auth.py:362`) — all key
  on `is_production`. A bypass-enabled deploy hands every anonymous visitor a
  session bound to `DEV_AUTH_EMAIL` (typically org admin).
- `ACCORD_ALLOW_WEAK_SECRETS` is honored even in production
  (`config.py:106-122` only requires non-empty `SESSION_SECRET_KEY`;
  `auth/session.py:44-53` skips the length floor when the flag is set) → forgeable
  session cookies / OAuth states.
- `SESSION_SECRET_KEY` strength is checked lazily at first sign
  (`auth/session.py:57,248`) — prod boots healthy-looking and fails on first login.

**Fix:** parse `environment` against an allowlist / invert to `is_development`;
reject `accord_allow_weak_secrets` in prod; enforce secret length at startup;
have `deploy/validate-deploy-env.py` fail on bypass/weak-secrets outside
`development`.

### T1.10 — Shared DB password; BYPASSRLS DSN in runtime containers [converged 2]

### T1.13 — Master-data mutations write zero audit events [converged 2, verified]

`write_mutation_event` is called from only three service files —
`run_workflow.py:456`, `run_posting.py:428,547`, `payroll_runs.py:755` —
**never** in `services/employees.py`, `services/pay_setup/*`,
`services/org_structure.py`, `services/members.py`, `services/identity.py`,
`services/bootstrap.py`, or `services/report_config.py`. (`artifacts.py:263` and
`report_generation.py:446` use `write_access_event`, which is correct for
downloads.) ADR-0009 §6 (line 218) mandates "Effective-dated master version append
→ audit_events (full entity snapshot)". Fraud scenario: change a beneficiary bank
account → post → restore — nothing in `audit_events` records it. Also unaudited:
`calculate` itself and draft input upsert/delete (only
`payroll_run_versions.calculated_by` records the actor).

**Fix:** emit `write_mutation_event` (before/after `entity_snapshot`) inside each
mutation's transaction. Design decision: audit detail is returned unmasked to all
`view_audit` holders (see M-sec-4) — decide the masking policy *before* dumping
PAN/account numbers into audit rows.

### T1.14 — Draft input writes skip the run lock [verified]

`payroll_runs.py:823-881,908-915`: `upsert_run_input`/`delete_run_input` use
`_get_run` (`:393-402`, no `FOR UPDATE`) unlike roster (`:636`) and metadata
(`:191` via `:405-422`). A concurrent in-flight `calculate` holds the lock but the
input write doesn't touch that row → the upsert passes `_require_draft`, commits,
and is silently absent from (or unexpectedly in) the produced version.
`expected_version` is a non-atomic read-then-write (`:839,859,866`) — two
concurrent upserts both read `version=N`, write `N+1`, last-writer-wins; and it's
ignored entirely on the create path (`:841-857`).

**Fix:** take the run `FOR UPDATE` in both functions, re-check status after the
lock; make the version check atomic (`UPDATE … WHERE version = :expected` +
rowcount, or lock the input row).

### T1.16 — Worker dies on a transient DB blip; shutdown can block forever [verified, reworded]

`jobs/worker.py:161`: `_list_active_org_ids()` is unguarded inside `run_once`, and
`run()` (`:138-153`) wraps the loop in no try — a pool checkout timeout/reset kills
the whole daemon; everything else in the cycle is deliberately guarded. The queue
factory at `:174` also sits outside the try. Separately, `_execute`'s join wait
(`:277-290`) has no timeout — a hung handler makes the process unkillable short of

**Fix:** wrap `run_once` body → `logger.exception` → idle-backoff; add a
shutdown grace deadline after which in-flight handler tasks are cancelled.

## Tier 2 — Medium

### Security / deploy hardening

- **T1.8 (downgraded) — CSRF residual is same-site only [verified]:**
  `SameSite=Lax` already blocks cookies on all cross-site POSTs, and
  `POST /post`+`/reverse` *require* `Idempotency-Key`
  (`backend/app/api/routes/run_posting.py:38,68`) → forced preflight → CORS
  allowlist protects them. The real residual: endpoints whose idempotency header
  is optional-or-absent (`/submit`, `/approve`, `/withdraw`, `/reject`, `/logout`,
  `/calculate`, `/validate`, `/reports/generate`, `/reports/export`) can be
  invoked header-less — exploitable only from a **same-site sibling app** (a
  compromised app sharing the parent domain), not arbitrary cross-site origins.
  Threat-model-mandated control still absent (`docs/threat-model.md:62-69,90`;
  `docs/security.md:48` admits the gap).
  **Fix:** non-HttpOnly CSRF cookie + required `X-CSRF-Token` header on
  cookie-authenticated mutations — cheap and closes the whole class.
- **M-sec-1** `GET /reports/jobs/{id}` returns `last_error` verbatim — worker stores
  2000-char traceback excerpts; every role with `generate_reports` (all six) gets
  internal paths/SQL text. (`routes/reports.py:211-216`, `jobs/worker.py:72-76,298-303`)
  → return `type(exc).__name__` + safe message only.
- **M-sec-2** Rate limiting exists on only 3 auth routes. `/calculate` runs the full
  engine per request; `/reports/generate`, `/reports/export`, artifact download
  are unbounded; `/auth/callback` is additionally unbounded while each call costs
  a WorkOS API round-trip. → apply `@limiter.limit` to those; consider making
  `calculate` idempotent.
- **M-sec-3** OAuth `state` is signed but **not bound to the initiating browser**
  (no nonce cookie) → login CSRF / session donation; `/auth/login` is unrate-limited
  so states are free. (`auth/session.py:255-273`, `routes/auth.py:287-333`) → set a
  10-min nonce cookie at `/login`, require match at `/callback`.
- **M-sec-4** Audit detail returns unmasked `before_state`/`after_state` to any
  `view_audit` holder — the employee-PII masking doesn't extend to audit payloads;
  today small only because sensitive entities aren't audited (T1.13). Decide the
  intended boundary before auditing PII-bearing entities.
  (`audit_events.py:41-46`, `audit_read.py:139-168`, `capabilities.py:53-93`)
- **M-sec-5** Unhandled 500s are handled by the outermost exception layer —
  `main.py:317`'s `add_exception_handler(Exception, handle_unhandled)` routes to
  `ServerErrorMiddleware`, which Starlette places **outside all user middleware**
  (verified against `Starlette.build_middleware_stack` source: `key in
  (500, Exception)` → `error_handler`, prepended before `user_middleware`). So the
  500 response bypasses SecurityHeaders/CORS middleware, **invisible to HTTP
  metrics**, and the `unhandled_error` log loses `request_id` (contextvars cleared
  first; only `X-Request-ID` is re-attached by the handler). → move the catch
  inside the inner exception layer or re-set context/headers in the handler.
  *(Note: one verification pass claimed `Exception` handlers go to the innermost
  ExceptionMiddleware — that is incorrect per Starlette source.)*

## What's solid (do not touch)

Core mechanisms verified by the second pass; secondary properties (per-role policy
coverage, two-sided denial counts, ancestry chain details, "no presigned URLs
anywhere") were confirmed in the primary review but not exhaustively re-verified.

- **RLS**: `ENABLE`+`FORCE`+`FOR ALL` with fail-closed
  `NULLIF(current_setting('app.organization_id',true),'')::uuid`; `NOBYPASSRLS`
  runtime roles; transaction-local `set_config(...,true)`; `SET ROLE` denial tests.
- **Money**: `Decimal`-only with a CI AST float-guard; exact-equality assertions
  incl. `.5`-paise boundaries; June-2026 golden fixture re-derived and cross-checked.
- **Workflow integrity**: `FOR UPDATE` run locks; maker-checker SoD; atomic
  status+approval+audit+outbox commits; content-hash binding submit→approve→post
  (but see M-data-2: the submit-time check is tautological).
- **Sessions**: opaque DB-backed signed ids; revocation + absolute + idle expiry;
  HttpOnly/SameSite=Lax/Secure-in-prod; separate salts for session vs OAuth state.
- **Webhooks**: signature+timestamp verify before parse; durable `ON CONFLICT`
  dedup in the handler's transaction; rollback-on-failure for redelivery.
- **Injection hygiene**: all raw SQL parameterized; Excel formula-prefix
  sanitization on every text path; opaque traversal-proof artifact keys; downloads
  stream through the audited API.
- **Release chain**: signature→checksum→manifest verification; `O_NOFOLLOW` path
  walks; fail-closed bootstrap.
- **Docs**: disclosures match code (CSRF gap, reveal auditing both admitted).
